# Arbejdsplan: omlægning til klinik- og lead-modellen

Status 2026-10-19. Planen fordeler arbejdet efter `docs/architecture.md` (v2.1) og bygger på `docs/omlaegning.md`. **Nyt 2026-10-19:** patientsiden flyttes til en Expo-app i `mobile/` (architecture 1.2 og 13); trin 7 afsluttes kun med backend- og `lib/`-rettelser (7.12), og trin 8 bygger appen til afleveringen ca. 2026-10-26. Den er et arbejdsredskab og slettes, når omlægningen er færdig. Arkitekturen er sandheden; afviger planen fra den, gælder arkitekturen.

## Spilleregler

- **Én opgave = én commit** på en feature-branch pr. byggetrin (fx `feat/omlaegning-trin-1`). PR til main pr. byggetrin.
- **Rækkefølge i hvert trin:** backend → ai-flow → frontend → reviewer → security (når login, databaseregler eller billeder er berørt) → tester.
- **Den gamle domænekode fjernes samlet i trin 0 (opgave 0.9, besluttet).** Den kan ikke køre mod det nye skema. Det, der kan genbruges, hentes fra git, når afløseren bygges: `git show e5cf7a04:<sti>` (sidste commit med den gamle model). Kolonnen "Udgangspunkt i git" peger på de filer.
- **Objektorienteret backend (architecture 2.1.1):** repositories i `models/` (arver `BaseRepository`), services og controllers er klasser. Filnavnet er klassenavnet i camelCase (`leadsRepository.ts` → `LeadsRepository`). Kode fra git skrives om til klasser, når den genbruges; den kopieres ikke ind som funktioner.
- **Færdig betyder** for alle kodeopgaver fra og med 0.9: `npx tsc --noEmit`, `npm run lint` og `npm run build` består, koden følger architecture 2.1-2.2, og de nævnte tests består. Sider er tjekket ved 390 px og 1280 px.
- Mangler et felt eller en route, som arkitekturen ikke beskriver, stopper agenten og beder architect om at opdatere dokumentet.
